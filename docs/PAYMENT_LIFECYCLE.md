# Payment-confirmed appointment lifecycle (Test)

Inspected main at 81f340e. `request_appointment` creates PENDING, validates full service intervals and takes a barber/day advisory lock. Manual appointments are created separately as CONFIRMED; existing manual behavior stays intact. PENDING now means **Pendiente de pago**.

Mercado Pago's webhook and return/status routes call `verifyAndConfirmAppointmentPayment`, query the official Orders API, match the appointment/order/currency/amount and call `confirm_appointment_from_payment`. Payway's server adapter records verified results in `payment_attempts` and calls `confirm_payway_attempt`. Both wrappers converge on the existing service-role-only `confirm_verified_appointment_payment`. That operation atomically marks CONFIRMED + deposit_paid + deposit amount and creates the deduplicated CONFIRMED outbox event. It retains cancellation/late-payment safeguards and now also refuses overlap with an active PENDING reservation.

The inspected database had **no server-side unpaid reservation expiration**. The browser remembered a reservation for ten minutes; Payway also enforced a ten-minute charge deadline. Neither released the stored appointment. The new private expiration RPC runs every minute through pg_cron, cancels unpaid holds after ten minutes, and records PAYMENT_EXPIRED + cancelled_at without deleting appointments or attempts. PROCESSING, UNKNOWN and APPROVED Payway attempts block expiration; CREATED attempts are closed on expiry. Rejected attempts permit a new attempt on the same appointment during its original deadline.

The Preview/Test Worker also runs a scheduled reconciliation hook every minute. It reuses the existing Mercado Pago Orders GET and confirmation boundary. Only an authoritative expired/canceled order with explicitly zero paid amount and no unsettled transactions is marked UNPAID_TERMINAL for expiration. API failure, missing credentials, incomplete evidence and nonterminal orders keep the hold. It never retries a charge. Maintenance is restricted to the exact Test Supabase URL. Payway UNKNOWN remains reserved for manual investigation until a provider-certified reconciliation contract is available; no guessed endpoint or automatic recharge is used.

`V2Appointments` in `v2/agenda.tsx` renders the actions. Pending/confirmed cards offer cancellation through the existing role-scoped RPC, and a validated wa.me deep link. Invalid phones disable that action. Existing Cobrar for confirmed appointments remains available. Terminal cards have no cancellation. No Confirmar/Rechazar/Enviar correo actions remain in V2. The status RPC refuses manual CONFIRMED; an additional database trigger prevents any legacy pending-to-confirmed/completed update unless it occurs within the privileged verified-payment operation. Direct staff UPDATE is also denied by existing RLS.

Cancellation persists first and creates its existing deduplicated CANCELLED outbox record. `updateRealAppointmentStatus` dispatches the returned claim via the existing Resend server function. Failure is recorded without reverting cancellation. Resend receives the event ID as Idempotency-Key. The short cancellation template links to KANI_APP_URL + /reservar (or the active request origin when no explicit URL is configured). Cancellation never calls refunds or changes payment rows.
